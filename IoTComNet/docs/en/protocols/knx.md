# KNXnet/IP

**Summary.** KNX is the building bus for lighting, blinds, heating and presence. Devices on a twisted-pair line (TP1)
have individual addresses (`area.line.device`, e.g. `1.1.4`) and communicate through group addresses
(`main/middle/sub`, e.g. `3/0/1`): a push-button writes "on" to `1/0/1`, and every actuator listening to `1/0/1`
reacts. Each group address carries one datapoint type (DPT). KNXnet/IP brings the line onto Ethernet (UDP 3671):
*tunnelling* gives one client a point-to-point connection through a KNX IP interface, *routing* multicasts every
telegram to `224.0.23.12`. `IoTCom.Net.Protocols.Knx` provides:

- Codecs (sans-I/O): `KnxIndividualAddress`, `KnxGroupAddress` (three-level, two-level and raw), `KnxCemiFrame`
  (cEMI L_Data.req/.con/.ind with control fields and group services), `KnxIp` (header, HPAI, CRI/CRD, device and
  service-family DIBs, every core, tunnelling and routing service), frame lanes for both, and `KnxDpt` for DPT 1, 2,
  3, 5, 6, 7, 8, 9 (KNX 2-byte float), 10, 11, 12, 13, 14, 16, 17, 18, 20.102 and 232.600 with names and units.
- `KnxTunnelClient`: connect (NAT mode by default), heartbeat every 60 s with three strikes, sequence counters,
  TUNNELING_ACK with one retry, L_Data.con checked (a negative confirmation is an error), repeated requests
  acknowledged but not delivered twice, `GroupValueReceived` for the whole line, `ReadAsync` waiting for the first
  response. **Read-only by default.**
- `KnxRouter`: a routing participant on the multicast group, with the same `IKnxGroupClient` API.
- `KnxDiscovery.SearchAsync`: SEARCH_REQUEST and the answers as `KnxDeviceInfo`.
- `KnxIpGateway`: a KNX IP interface and router in software — search and description, up to N tunnels with
  individual addresses, heartbeat supervision, acknowledgements with retry (an unresponsive client is disconnected),
  L_Data.con, forwarding of the line to every tunnel and to the multicast group.
- `KnxBus` (an in-process TP1 line) and `KnxBuildingSimulator`: an office floor with switching, dimming and blind
  actuators, room controllers with heating valves and HVAC modes, presence detectors and a weather station, with the
  group address plan in `GroupAddresses`.

Following the design, KNX is managed C# over `System.Net.Sockets` (no Rust twin). The codecs are checked against
`/conformance/knx.json`, generated by an independent Python reference.

## When to use it

- Visualisations, dashboards and logging for KNX installations (offices, hotels, schools, homes).
- Bridging KNX to MQTT, OPC UA or a building management system.
- Testing a KNX integration without an installation: the gateway and the floor run anywhere, also behind real UDP.

## Installation

```bash
dotnet add package IoTCom.Net.Protocols.Knx --prerelease    # also part of the IoTCom.Net meta-package
```

## Quickstart

Monitor and read a real installation:

```csharp
using IoTCom.Net.Protocols.Knx;

await using var knx = KnxTunnelClient.Create(o => o.UseGateway("192.168.1.10"));   // read-only
knx.GroupValueReceived += e => Console.WriteLine(e);
await knx.ConnectAsync();
double temperature = (double)await knx.ReadAsync("3/0/1", "9.001");
```

Write, after opting in:

```csharp
await using var knx = KnxTunnelClient.Create(o => o.UseGateway("192.168.1.10").AllowWrites());
await knx.ConnectAsync();
await knx.WriteAsync("1/0/1", "1.001", true);      // light on
await knx.WriteAsync("2/1/1", "5.001", 75);        // blind to 75 %
await knx.WriteAsync("3/1/1", "9.001", 21.5);      // set point
```

An installation without hardware, reachable by ETS or any KNXnet/IP tool on this machine:

```csharp
await using var bus = new KnxBus();
var floor = new KnxBuildingSimulator(bus);
await using var router = KnxIpGateway.Create(o => { o.UseUdp(KnxIp.Port); o.Bus = bus; });
await router.StartAsync();
// call floor.Step(seconds) periodically to move blinds and temperatures
```

Find interfaces: `await KnxDiscovery.SearchAsync()`. Routing: `KnxRouter.Create()` joins `224.0.23.12:3671`.

## Safety

Group writes switch lights, drive blinds and motors and change heating set points in occupied buildings. The tunnel
and the router refuse them until `AllowWrites()`; the CLI needs `--allow-write` and asks before writing to a real
installation, and the Gallery has a write lock. KNXnet/IP has no authentication: keep interfaces on a separate
network and never expose UDP 3671 to the internet. KNX Secure (IP Secure, Data Secure) is not implemented.

## Tools

```bash
iotcom knx demo [--allow-write]                                   # discovery, a tunnel and the office floor
iotcom knx discover                                               # SEARCH_REQUEST on the local network
iotcom knx monitor --gateway 192.168.1.10                         # group monitor (read-only); --routing for multicast
iotcom knx read 3/0/1 --dpt 9.001 --gateway 192.168.1.10
iotcom knx write 1/0/1 on --dpt 1.001 --gateway 192.168.1.10 --allow-write
iotcom knx decode "29 00 BC E0 11 04 18 01 03 00 80 0C 33" --dpt 9.001
```

Every command takes `--sim` to use the in-process router and floor instead of an installation. Captures map KNXnet/IP
to UDP 3671, so Wireshark decodes them; the VS Code extension decodes `knxip` and `cemi`. Gallery: *Office floor over
KNX*.

## Testing

Codec tests cover addresses (three-level, two-level, raw, out of range), DPT formatting and range checks, and frame
lanes. The 56 shared vectors cover every supported DPT including the KNX float's edges (`0x7FFF` is reserved for
invalid data), cEMI frames with short and long values, additional information and malformed frames, and KNXnet/IP
connect, connection state, tunnelling, routing and malformed headers.

Session tests run the router, the floor and clients over an in-memory UDP network: reads and read-only refusals;
a write reaching the actuator with the status seen by a second tunnel but not echoed to the sender; heartbeats,
`E_NO_MORE_CONNECTIONS` and freed channels after disconnect; a repeated tunnelling request acknowledged twice but
applied once; a client that stops acknowledging being dropped; discovery; and routing participants writing and
reading.

## Limitations

KNX Secure, KNXnet/IP over TCP, device management (individual address programming, property access, memory reads),
extended frames and long frames are not implemented. The tunnel uses the link layer (no busmonitor mode). Routing
flow control (ROUTING_BUSY) is not acted on. The software router speaks only to its in-process line, not to a real
TP1 coupler.
