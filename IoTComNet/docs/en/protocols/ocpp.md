# OCPP 1.6J and 2.0.1

**Summary.** The Open Charge Point Protocol (OCPP) connects an EV charger to its back office, the CSMS (charging
station management system; "central system" in 1.6). The charger opens a WebSocket to the CSMS, with its identity as
the last path segment and the OCPP version as the subprotocol (`ocpp1.6` or `ocpp2.0.1`). Both sides then exchange
small JSON arrays: a CALL `[2, id, action, payload]` is answered by a CALLRESULT `[3, id, payload]` or a CALLERROR
`[4, id, code, description, details]`. `IoTCom.Net.Protocols.Ocpp` provides:

- `OcppFrame`, the sans-I/O RPC codec: parsing with the error code a receiver must answer with (1.6 and 2.0.1 use
  different names), formatting, and the frame lane (`DescribeFields`, UTF-8 byte offsets).
- `OcppSession`, the RPC framework over a WebSocket: CALL/CALLRESULT pairing with one outstanding CALL per side,
  timeouts, typed (`On<TRequest, TResponse>`, `CallAsync`) and raw JSON handlers, NotImplemented and format errors
  answered automatically, and requests handled off the receive loop so handlers may call back.
- Typed messages in `V16` and `V201` (core, smart charging and remote trigger profiles) with source-generated JSON,
  so the package is trimmable and NativeAOT compatible. `OcppCatalog` finds the types of an action and validates a
  payload against them.
- `OcppChargePoint`, the charger side: `ws://` and `wss://` through `ClientWebSocket` (Basic authentication for
  security profiles 1 and 2, client certificates for profile 3), or any IoTCom transport (`UseInMemory`, `UseTcp`).
- `OcppCsms`, a small CSMS: its own HTTP/1.1 WebSocket upgrade over `UseTcp` / `ListenInMemory` (optional TLS and
  password check), or `AcceptWebSocketAsync` for sockets accepted by ASP.NET Core. It answers boot, heartbeat,
  status, authorization (an allow-list of id tags), transactions and meter values, keeps a live `OcppStation` model,
  and sends version-independent commands: `RemoteStartAsync`, `RemoteStopAsync`, `ResetAsync`, `UnlockAsync`,
  `SetAvailabilityAsync`, `SetPowerLimitAsync` (charging profiles), `ReadConfigurationAsync`,
  `WriteConfigurationAsync` and `TriggerAsync`.
- `OcppChargePointSimulator`: a complete charger for either version with connectors, an EV model (state of charge,
  taper above 80 %, the CSMS's power limit), meter values, heartbeats, reconnects, and answers to every command above.

Following the design, OCPP is managed C# (JSON over WebSocket, no Rust twin). The RPC codec and 16 schema-valid
payloads are checked against `/conformance/ocpp.json`, generated by an independent Python reference.

## When to use it

- Building or testing a CSMS: run dozens of simulated chargers of both versions against it.
- Building charger firmware or a gateway on .NET (Linux on an embedded controller).
- A small private CSMS for a depot, a building or a lab, or a bridge from chargers to a building management system.

## Installation

```bash
dotnet add package IoTCom.Net.Protocols.Ocpp --prerelease    # also part of the IoTCom.Net meta-package
```

## Quickstart

A charger against an existing CSMS:

```csharp
using IoTCom.Net.Protocols.Ocpp;
using V16 = IoTCom.Net.Protocols.Ocpp.V16;

await using var cp = OcppChargePoint.Create(o =>
{
    o.UseCsms("wss://csms.example.com/ocpp/");   // the identity is appended: …/ocpp/CP-001
    o.Identity = "CP-001";
    o.Version = OcppVersion.Ocpp16;
    o.Password = Environment.GetEnvironmentVariable("OCPP_PASSWORD");
});
cp.On<V16.RemoteStartTransactionRequest, V16.RemoteStartTransactionResponse>((r, ct) =>
    ValueTask.FromResult(new V16.RemoteStartTransactionResponse { Status = OcppGenericStatus.Accepted }));
await cp.ConnectAsync();
var boot = await cp.CallAsync(new V16.BootNotificationRequest { ChargePointVendor = "Acme", ChargePointModel = "W22" });
```

A CSMS with a simulated charger:

```csharp
await using var csms = OcppCsms.Create(o => o.UseTcp(IPAddress.Any, 8887));   // ws://host:8887/ocpp/{identity}
csms.TransactionStopped += (station, tx) => Console.WriteLine($"{station.Identity}: {tx}");
await csms.StartAsync();

await using var charger = OcppChargePointSimulator.Create(o => { o.UseCsms("ws://127.0.0.1:8887/ocpp/"); o.Version = OcppVersion.Ocpp201; });
await charger.StartAsync();
await charger.PlugInAsync(1, socPercent: 20);
await charger.PresentCardAsync(1, "04A1B2C3");
await charger.StepAsync(TimeSpan.FromMinutes(30));   // or AutoRun = true
```

Inside ASP.NET Core, accept the socket yourself and hand it over:

```csharp
app.Map("/ocpp/{id}", async (HttpContext http, string id) =>
{
    var socket = await http.WebSockets.AcceptWebSocketAsync("ocpp2.0.1");
    await csms.AcceptWebSocketAsync(socket, id, OcppVersion.Ocpp201, http.Connection.RemoteIpAddress?.ToString() ?? "");
});
```

## Safety

Remote start and stop, reset, unlock, availability, configuration and charging limits change what a charger and the
car connected to it do. `OcppCsms` refuses them until `AllowCommands()`; reads (configuration, triggers) stay
allowed. The Gallery and the CLI put a write lock in front of them (`--allow-write`). Passwords are never logged.
Use `wss://` with Basic authentication or client certificates outside a lab, and keep `AcceptAnyServerCertificate`
off.

## Testing

Frame tests cover CALL/CALLRESULT/CALLERROR formatting, the OCPP field names in JSON (`idToken`, `Sample.Periodic`),
missing required fields, and byte offsets of the frame lane. The 35 shared vectors include the specifications'
examples, 13 malformed messages with the error code each version answers with, and 16 typed payloads that must
re-serialise unchanged.

Session tests run the CSMS and simulators of both versions in-process: boot and status; a card that starts a
transaction and unplugging that ends it with the right energy; unknown cards refused; commands refused in read-only
mode, then remote start, a power limit the car obeys, and remote stop; configuration reads in read-only mode and
writes after; NotImplemented and format errors; a reset that reboots the charger; and a dropped link that reconnects.
A TCP test runs `ClientWebSocket` against the CSMS's own upgrade with Basic authentication, and a wrong password is
refused.

## Limitations

The typed messages cover the core, smart charging and remote trigger profiles; firmware management, local
authorization lists, reservations, diagnostics/logs, display messages, ISO 15118 certificates and the 2.0.1 device
model reports (`GetBaseReport`/`NotifyReport`) go through the raw JSON API (`CallAsync(action, payload)`). The CSMS
applies one TxDefaultProfile limit per connector; it does not compose profile stacks or schedules over time. Offline
transaction queueing in the simulator is not implemented. OCPP 2.1 is not supported.
